# 面试问答笔记

这份笔记只记录能由当前代码和测试支撑的内容，不虚构 QPS、用户量或线上指标。

## 1. 如何防止同一个用户重复报名？

分三层：

1. 前端在报名按钮请求期间设置 loading，减少误触。
2. 服务端在活动行锁内查询 `registrations` 中当前用户在该活动的记录。
3. 数据库使用 `(event_id, user_id)` 唯一索引兜底。

服务端的判断不是“请求有没有重复”，而是“这个用户和这个活动的报名记录是否已经存在”。如果已有 `CONFIRMED / WAITLISTED / PROMOTED / CHECKED_IN`，直接返回当前记录。`CANCELED / EXPIRED` 可以选择重新报名。

如果面试官追问“两个人同时注册同一个账号怎么办”，回答：活动行锁会把同一活动的报名串行化，唯一索引再防止并发插入产生两条记录。

## 2. 怎么防止双击或网络重试导致重复提交？

核心不是加一个前端防抖，而是让业务接口具备幂等性：

- 同一用户、同一活动的有效报名，重复调用返回同一条记录。
- 签到接口如果已经是 `CHECKED_IN`，直接返回已有签到结果。
- 余额类场景通常需要幂等键或去重表；本项目使用业务唯一键 `(event_id, user_id)`，成本更低。

前端 loading 只是体验优化，不能作为一致性保证。

## 3. 取消报名和候补递补怎么保证事务一致性？

取消流程在一个事务中执行：

1. `SELECT ... FOR UPDATE` 锁定活动行。
2. 查询并锁定当前报名记录。
3. 把当前报名改为 `CANCELED`。
4. 如果当前报名原本占座，查询候补队列第一名并锁定。
5. 有下一位：把下一位改为 `PROMOTED`，写入确认截止时间。
6. 没有下一位：把活动 `occupied_count` 减一。

活动行锁和报名行锁的组合顺序固定，避免“取消”和“确认”同时锁住不同行造成死锁。

## 4. 为什么这个场景不用 Redis 或分布式锁？

当前是单体 Spring Boot + 单 MySQL，活动规模和并发量都不需要跨服务协调。

MySQL 行锁已经可以提供：

- 单活动名额变更的串行化。
- 取消、递补和计数变更的同事务原子性。
- 唯一索引兜底重复报名。

引入 Redis 会多出缓存一致性、锁续期、宕机恢复和运维成本，却不会给校园活动带来足够的收益。真正需要扩展时，再把名额预扣拆成独立服务并使用 Redis/消息队列更合理。

面试时不要把“不用 Redis”说成“不会 Redis”，而要说清楚规模、成本和一致性的取舍。

## 5. 为什么 `PROMOTED` 也占用名额？

因为递补者已经拿到了这个座位的优先使用权。系统需要给他 10 分钟确认窗口，在这段时间内不能让第三个学生把这个座位抢走。

时间线：

1. A 取消，释放一个座位。
2. B 从 `WAITLISTED` 变成 `PROMOTED`，座位转给 B 保留。
3. B 确认，变成 `CONFIRMED`。
4. B 超时，变成 `EXPIRED`，系统再递给 C。

所以 `occupied_count` 包含 `CONFIRMED + PROMOTED + CHECKED_IN`。

## 6. 怎么处理确认和超时的竞态？

两处代码都会先锁活动行和报名行，并重新检查数据库里的当前状态与截止时间：

- 学生点击“确认参加”的接口。
- 定时扫描过期递补的任务。

无论谁先拿到锁，后拿到锁的一方都会看到最新状态，只能有一个操作成功。不能只在 Java 内存里判断时间，因为 Java 线程调度和多实例部署都会破坏这种假设。

## 7. 二维码签到 token 怎么设计？

管理员生成一个活动级 JWT：

- `sub = eventId`
- `type = CHECK_IN`
- 默认 5 分钟过期
- HMAC-SHA256 签名

学生扫码打开签到页后，页面仍然要求登录，再把 token 发给后端。后端校验签名、过期时间和活动状态，再查询当前用户的报名记录。

二维码 token 只证明“这是当前活动的签到入口”，不替代学生身份。因此不能只靠 token 就完成签到。

## 8. 签到为什么是幂等的？

签到前会先锁定该用户在该活动的报名记录：

- 如果已经是 `CHECKED_IN`，返回已有签到时间，不重复更新。
- 如果只是 `CONFIRMED`，更新为 `CHECKED_IN`。
- 如果候补、取消或不存在，返回业务错误。

数据库中的报名记录只有一行，避免了为同一个人插入多条签到记录。

## 9. 为什么用 JWT，不用 Session？

项目是前后端分离的 Vue3 + Spring Boot，JWT 适合无状态接口授权。

设计包含：

- BCrypt 密码哈希。
- 登录成功后签发 JWT。
- 过滤器解析 Bearer token。
- `ROLE_STUDENT` 和 `ROLE_ADMIN` 控制 `/api/admin/**`。

代价是 MVP 没有服务端主动注销和 token 撤销列表，生产环境需要更完整的会话管理、密钥轮换和刷新策略。

## 10. 怎么证明没有超卖？

`RegistrationConcurrencyTest` 使用真实 MySQL 和测试库，创建 20 个学生并发争抢 5 个名额，最终断言：

- `occupied_count = 5`
- `CONFIRMED` 数量 = 5
- `WAITLISTED` 数量 = 15

这不是虚构 QPS，只是验证并发正确性。简历上应写测试场景和结果，不写没有压测过的吞吐指标。

## 11. 如果面试官问“这个项目有什么不足”？

可以主动承认：

- 单活动报名会串行化，热点活动吞吐有限。
- 结束活动后不自动生成缺席记录。
- 没有消息通知，递补确认依赖用户主动打开页面。
- JWT 没有撤销列表。
- 二维码只降低随意伪造，不能证明学生物理上一定在场。
- Excel 导出和名单接口没有大型活动分页。

能说清边界，比硬说“完全生产级”更可信。
