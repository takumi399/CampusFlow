# ADR-0001：使用 MySQL 行锁与唯一索引控制活动名额

- 状态：Accepted
- 日期：2026-11-08

## 背景

校园活动报名会出现多个学生同时争抢最后一个名额的情况。项目使用单体 Spring Boot 应用和单个 MySQL 数据库，预计并发量远低于电商秒杀场景。

需要同时保证：

1. 占位名额不超过活动名额。
2. 同一个学生对同一个活动只有一条有效报名记录。
3. 取消报名和候补递补在同一个事务中完成。

## 决策

使用 MySQL 单库方案：

- 报名、取消和递补都以活动行为并发控制入口，通过 `SELECT ... FOR UPDATE` 锁定活动记录。
- 使用 `(event_id, user_id)` 唯一索引兜底重复报名。
- 活动表维护 `occupied_count`，其含义包括确认报名、已签到和待确认递补。
- 所有名额变更在同一个数据库事务中完成。
- 不在 MVP 中引入 Redis 预扣库存或分布式锁。

## 结果

优点：

- 数据一致性只依赖一个数据库，事务边界清晰。
- 校园活动规模下，单活动报名串行化带来的吞吐损失可以接受。
- 面试时可以清楚解释为什么这个规模不需要分布式锁。

代价：

- 同一个活动的报名请求会串行执行，热点活动吞吐受限。
- 如果未来需要跨服务或跨数据库扩展，需要重新设计名额预扣和最终一致性。
- `occupied_count` 必须与报名状态变更同步维护，否则会出现计数漂移。

## 备选方案

- Redis 预扣库存：吞吐更高，但增加缓存一致性、故障恢复和运维成本，当前规模不划算。
- 纯乐观锁重试：读多写少场景合适，但热点名额冲突时重试成本高，而且取消和递补仍需额外锁。
- 数据库唯一索引但不锁活动行：能防止重复报名，但不能可靠防止超卖。
